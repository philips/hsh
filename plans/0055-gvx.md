# 0055: Replace podman and runsc with gvx

Status: plan. Nothing implemented yet.

Move hsh's sandbox from rootless podman + runsc (`internal-docs/gvisor.md`)
to [gvx](https://github.com/gfire-sigs/gvx), a gVisor fork that runs OCI
images inside one unprivileged process on Linux (systrap) and Apple Silicon
macOS (Hypervisor.framework), with an embeddable pure-Go SDK
(`z.gfire.dev/gvx/pkg/gvx`, `CGO_ENABLED=0`).

Goals:

1. macOS support (`darwin/arm64`).
2. No podman: hsh pulls images, lays out root filesystems, and manages the
   sandbox lifecycle itself.
3. The sandbox runs in-process through the gvx Go SDK instead of exec'ing
   runsc through podman.

The user's guess at the order was 3, 2, 1. The investigation below agrees,
with a phase 0 first and phase 2 split so that macOS can start before all of
podman is gone.

## What gvx gives us (as of v0.24, Nov 2026)

Read from the repository at `e4e6b7b`. Items marked *verify* are from docs
only and need the spike.

| Need | gvx feature |
|---|---|
| Run an OCI image | `gvx.New(ctx, gvx.Config{OCIImage, Argv, Envv, User, WorkDir, Hostname, ...})`, `Sandbox.Run`/`Wait`/`Close` |
| Pull images | `pkg/oci`: registry client, Docker credential helpers, multi-arch manifests, OCI and `docker save` archives, layers compiled to cached EROFS files, pull policies `missing`/`always`/`never` |
| Persistent root filesystem | `Config.RootVolume`: an ext4lite image file as the overlay upper layer (replaces podman's container layer and `--overlay2=none`) |
| Bind mounts | `Config.WorkspacePath`, `Config.Mounts` (bind, named volume, tmpfs), via `hostfs` pinned to `os.Root` |
| TTY | `Config.TTY` with `Stdin`/`Stdout`; window size and `SIGWINCH` read from the host terminal passed in |
| exec into the sandbox | control protocol `gvx-ctrl/2` over an owner-only Unix socket: `exec.start` (argv, env, workdir, user, PTY, resize, signal, exit event) |
| Forward into the sandbox | `net.dial` dials a guest TCP port inside the sandbox netstack (`loopback_fallback` reaches `127.0.0.1` listeners) |
| Suspend | `lifecycle.pause`/`unpause`; `Sandbox.Checkpoint` / `gvx.Restore` work under lockdown (replaces 0052's runsc pause and the missing `checkpointgofer`) |
| Resource limits | `Config.Resources` (memory, CPU, pids), which rootless runsc under podman could not do (`--ignore-cgroups`) |
| Host confinement | `pkg/hostlockdown`: Landlock + seccomp on Linux, Seatbelt on macOS. Applied by `gvx.New` and **irreversible for the process** |
| setuid | ignored unless `Config.AllowSUID`, so hsh's setuid stripping is not needed |
| Networking | `NetModeNAT` (L4 NAT to host sockets, DNS relay at `10.0.2.3`, `StreamInterceptor` hook), `NetModeWireGuard` (in-memory wireguard-go over one UDP socket), `NetModeNone` |

## Gaps and design decisions

### Network: no raw-packet attachment

Today runsc's `--network-proxy-path` hands every IP packet to the proxy's own
netstack over a `SOCK_SEQPACKET` socket, and the proxy decides per flow by
SNI, Host header, or DNS-answer name (`internal/proxy/netstack.go`). gvx has
no equivalent mode. Options:

- **A. Add a packet-link mode to gvx (recommended).** A `NetModeLink` with
  `Config.PacketConn` (or a `stack.LinkEndpoint`) that attaches guest `eth0`
  to an embedder-supplied packet transport opened before lockdown. This is
  runsc parity, lives in gvx's Tier 1 packages (`pkg/gvx`, `pkg/netbackend`),
  and keeps hsh's proxy unchanged above the link layer. Upstream it; carry
  it as a fork patch until it lands.
- **B. WireGuard mode with the proxy as the peer.** Needs no gvx change: the
  proxy runs wireguard-go with a tun device that feeds its existing netstack,
  on a loopback UDP port. Costs crypto per packet and a key exchange per
  session. *Verify*: in wg mode gvx still answers DNS at `10.0.2.3` from the
  host's resolvers, which would be a DNS path around the proxy; it must be
  off or pointed at the proxy. Fallback if A is refused.
- **C. NAT mode with `StreamInterceptor`.** Rejected. gvx dials the
  destination before calling the interceptor (so a denied host is contacted,
  and the SNI cannot choose the dial), UDP and DNS go to the host directly,
  and the interceptor runs in the sandbox process, so secrets would live in
  the process a sentry escape lands in.

The proxy's link endpoint must become portable: `fdbased` is Linux-only
(it is the only reason `internal/proxy` does not build for darwin). Use a
channel endpoint with a read/write loop. macOS has no AF_UNIX
`SOCK_SEQPACKET`, so the transport is a length-prefixed `SOCK_STREAM` (see
[the transport probe](#transport-probe-macos-and-linux)).

hsh imports `gvisor.dev/gvisor/pkg/tcpip`; gvx carries its own copy as
`z.gfire.dev/gvx/pkg/tcpip`. Switch the proxy to gvx's copy so the binary
holds one netstack.

#### How runsc implements `--network-proxy-path`

Read from the runsc tree that gvx carries (gVisor release-20261123.0; hsh
embeds release-20261026.0). gvx's SDK does not use this code. It is the
reference for option A.

The code runs in two processes: the runsc host process
(`runsc/sandbox/network.go`) and the sentry (`runsc/boot/network.go`).

1. **Validation** (`runsc/config/config.go`). The path must be absolute.
   It needs `--network=sandbox`. It cannot be combined with XDP,
   `--netgofer`, or `--rdmaproxy`. `UseNetworkProxy()` is true for
   `--network-proxy-path` and for runsc's own sidecar, `--netgofer`. Both
   share the link code below.
2. **Scrape the container netns** (`createInterfacesAndRoutesFromNS`). As
   usual for sandbox networking, runsc joins the netns that podman made
   (pasta's interface) and reads its links, addresses, routes, and MTU.
   `primaryInterface` picks the interface that holds the default IPv4/IPv6
   gateway; without one it picks `eth0` or the only link. The two defaults
   must agree.
3. **Dial the peer** (`dialExternalUDS`). It runs in the runsc host
   process, not the sentry, so the path is resolved in the host's mount
   namespace, and the sentry's seccomp filter never needs `socket` or
   `connect`.
   - It opens an `AF_UNIX` `SOCK_SEQPACKET` socket and calls `connect`
     once, with a 5 s `SO_SNDTIMEO`. A peer that is not listening fails the
     sandbox start, which is why hsh waits for the socket before starting
     the workspace.
   - `EPROTOTYPE` means the peer is not `SOCK_SEQPACKET`. `EAGAIN` means
     its accept backlog is full.
   - It sets 4 MB send and receive buffers: `SO_*BUFFORCE`, falling back
     to `SO_*BUF`, which `net.core.{r,w}mem_max` caps. A failure is only a
     warning.
4. **Keep the host addresses.** On every other link runsc deletes the
   host-side addresses after copying them. It skips that for the primary
   link, so the guest and pasta's interface both hold the same address.
   The guest's address, prefix, routes, and MTU (65520 under pasta, which is
   why the proxy uses `netstackMTU = 65520`) all come from the container
   netns.
5. **Mark the link** (`configureProxyLink`).
   - `IsProxy = true`.
   - `NumChannels` is forced to 1.
   - When TX checksum offload is on, RX checksum offload is forced on.
     Defaults are `--tx-checksum-offload=false` and
     `--rx-checksum-offload=true`, so the guest does not verify L4 checksums
     on packets from the peer.
   - The socket fd goes to the sentry in the urpc `FilePayload` of
     `ContMgrSetNetworkArgs`, in place of the AF_PACKET sockets.
6. **The sentry builds an `fdbased` endpoint** on a dup of the fd. It
   differs from a normal link in four ways:
   - **No Ethernet header** (`EthernetHeader: mac != "" && !IsProxy`). Each
     `SOCK_SEQPACKET` record is one bare IPv4 or IPv6 packet, in both
     directions.
   - **`Readv` dispatch, not `RecvMMsg`.** A 0-byte read (the peer
     closed) then stops the dispatcher instead of spinning. The link is
     not redialed. If the proxy goes away the guest has no network until
     the sandbox restarts.
   - **No neighbor table.** Static ARP entries are not copied.
   - **`AllowExternalIPv4LoopbackTraffic`** is set only for
     `--netgofer=proxy-loopback`, never for an external peer.

   GSO, GRO, and the qdisc (FIFO by default) apply as on any `fdbased`
   link.
7. **Restore.** `Sandbox.Restore` runs `setupNetwork(..., isRestore=true)`
   again, which dials the path afresh. The peer sees a new connection, and
   hsh's proxy starts a new stack for each connection.

The peer contract, then: listen on `SOCK_SEQPACKET`, accept one
connection per sandbox start, and exchange one IP packet per record with no
framing or L2 header. The peer gets packets from the guest's real
(pasta-assigned) source address to any destination, so it must run
promiscuous with spoofing on. It may send packets without L4 checksums,
since the guest skips the check. hsh's proxy does exactly this: `fdbased`
with the zero-value (`Readv`) dispatch mode, no Ethernet header,
promiscuous and spoofing on, and catch-all routes.

`--netgofer` (`runsc/gofer/net/netgofer.go`) is runsc's own peer. It is a
`socketpair` instead of a dialed path, and runsc starts it in the sandbox's
netns under its own seccomp filter (`runsc/gofer/net/filter`), with an
optional egress filter. It is about 1,300 lines and a useful second
reference.

#### What option A needs in gvx

- `Config.NetworkMode = "link"` with a pre-connected transport supplied by
  the embedder: an `*os.File` (`SOCK_SEQPACKET`) on Linux. The SDK dials
  nothing, so lockdown needs no new socket rule. There is no netns to
  scrape, so the embedder supplies the guest address, prefix, gateway, and
  MTU, or gvx uses its NAT defaults (`10.0.2.15/24`, gateway `10.0.2.2`).
  hsh's proxy accepts any source address, so the defaults work.
- No DNS relay on this link. gvx's relay at `10.0.2.3` belongs to the NAT
  and WireGuard backends. In link mode every packet must reach the peer.
- One transport on every host: an AF_UNIX `SOCK_STREAM` carrying
  length-prefixed IP packets, served by a portable endpoint (a `channel`
  endpoint plus a read loop and a write loop over a `net.Conn`). It is not
  `fdbased` with `SOCK_SEQPACKET` as in runsc, because macOS has no
  `SOCK_SEQPACKET` and `fdbased` is Linux-only. One code path also keeps
  the Linux and macOS behavior the same. gvx's seccomp allowlist
  (`pkg/gvx/syscallfilter_linux.go`) must allow reads and writes on the
  fd.
- Framing: a 4-byte big-endian length, then the packet. That leaves room
  for packets larger than 64 KiB if GSO is ever used. The writer sends the
  header and the packet in one `writev`. The reader rejects a length of
  zero or one larger than the MTU, and closes the link. RX checksum offload
  is on, as in runsc. The MTU is 65520, as today.
- Both ends set 4 MiB `SO_SNDBUF`/`SO_RCVBUF`. The macOS stream default is
  8 KiB.
- Checkpoint and restore: `gvx.Restore` must accept a new transport, as
  runsc redials on restore. The manifest records the mode, not the fd.

hsh's proxy listens on a second socket, `netstack/stream`, for gvx
sessions. It keeps the `SOCK_SEQPACKET` listener only while the runsc
runtime exists (phases 3 and 2a, Linux only). Both listeners feed the same
per-connection stack.

#### Transport probe (macOS and Linux)

`plans/prototype/unix-packet-transport` (`go run .`) was run on an M-series
MacBook Air (macOS, Darwin 27.2.0) and on a Linux x86_64 host (Fedora,
kernel 7.2). Throughput is a one-way loop through a `socketpair` with 4 MiB
buffers. The two machines are different hardware, so compare transports
within a column, not hosts across columns.

| | macOS | Linux |
|---|---|---|
| `SOCK_SEQPACKET` | **not supported**: `EPROTONOSUPPORT` from `socket`/`socketpair`, and `net.Listen("unixpacket")` fails | works: EOF on close, 6.8 GB/s at 65520 B |
| `SOCK_DGRAM` default buffers | `SO_SNDBUF` 2048 (`net.local.dgram.maxdgram`), so the largest datagram is 2048 B | 212,960 B |
| `SOCK_DGRAM` with 4 MiB buffers | largest datagram 4,194,288 B; 65520 B works | ≥ 4 MiB |
| `SOCK_DGRAM`, peer closed | read and write fail with `ECONNRESET` on a `socketpair` | read gives `EAGAIN` (no EOF), write gives `ECONNREFUSED` |
| `SOCK_STREAM` default buffers | 8 KiB (`net.local.stream.*space`); 4 MiB is granted | 208 KiB; 4 MiB is granted as 8 MiB |
| `SOCK_STREAM`, peer closed | EOF, `EPIPE` | EOF, `EPIPE` |
| 65520 B packets: DGRAM / STREAM | 26.5 / 25.1 GB/s | 6.7 / 7.0 GB/s |
| 1500 B packets: DGRAM / STREAM | 2.5 / 2.7 GB/s | 0.9 / 1.2 GB/s |
| `sun_path` limit | 104 B: hsh's session socket under `~/Library/Application Support` is 82 B here, and one under the `/var/folders/.../T` temporary directory is 83 B | 108 B |

Why `SOCK_STREAM` and not `SOCK_DGRAM`:

- Its throughput is the same. The probe writes fixed-size chunks with no
  framing, but a 4-byte header is negligible beside a 1500 B packet.
- A peer that goes away is an EOF on both hosts. With datagrams, Linux
  gives no signal at all, and macOS reports it only on a connected pair.
- A datagram socket bound to a path has no connections. Each sandbox would
  need its own bound client address for the proxy to reply to. A stream
  listener gives one accepted connection per sandbox start, which is what
  the proxy's per-connection stack already expects.
- The 2 KiB macOS default for datagrams fails as soon as one side forgets
  to raise `SO_SNDBUF` (9000 and 65520 B sends got `EMSGSIZE`). A stream
  has no per-message limit.

### Process model: one supervisor per session

Lockdown is irreversible and the sandbox lives as long as its process, while
sessions must outlive `hsh run` (detach, reaper). So each session gets a
supervisor process, a new argv[0] role `hsh-sandbox`, started detached
(`setsid`) by `hsh run`/`hsh resume`. It:

- opens everything first: image layers, `RootVolume`, workspace and mounts,
  the proxy link, the control socket `sessions/<id>/control.sock`, and
  checkpoint files; then calls `gvx.New`, which locks the process down;
- does nothing of its own afterwards. Under lockdown, any syscall outside
  gvx's seccomp allowlist kills the process with `SIGSYS` (seen with
  `getrusage` and the Go CPU profiler's timers), not `EPERM` as the gvx docs
  say. So no pty relay, accept loop, or logging that might add a syscall
  runs in it;
- exits with the guest's PID 1.

PID 1's terminal comes from a host terminal: gvx reads the size from the
fd passed as `Stdin`/`Stdout` and resizes when that terminal does. A second
process per session, the keeper (`hsh-keeper`, conmon's role, no lockdown,
no secrets), therefore:

- allocates the pty pair and keeps the master;
- starts the supervisor with the slave as its stdio and controlling
  terminal (`setsid`, `Setctty`);
- serves the master on `sessions/<id>/attach.sock` (bytes plus resize
  messages, applied with `TIOCSWINSZ` on the master);
- writes `sessions/<id>/sandbox.pid` and records the supervisor's exit
  status.

Detach closes the attach connection; the keeper and the shell keep running.
`hsh run`'s relay (`internal/relay`) connects to the attach socket directly
instead of running `podman attach` on a pty. The keeper sees the guest's
terminal bytes, as conmon does today.

The session's shell cannot be an `exec.start` session instead: an exec'd
process outlives its client (it keeps running after the client is killed),
but its stdio cannot be reattached.

### Proxy process (phase 2)

Without podman the proxy becomes a host process (`hsh-proxy` role, started
detached per session). Today the container keeps it from seeing other
sessions' state; replace that with `hostlockdown.Apply` in the proxy: read
access to its session's files, write access to `proxy/`, outbound network
allowed. On Linux `hostlockdown` requires the embedder's seccomp filter, so
the proxy needs its own (or Landlock only, as a first step). Two behavior
changes to handle:

- The proxy is on the host network, not behind pasta. `127.0.0.1`, the LAN,
  and the host's own services become reachable destinations. The proxy must
  refuse loopback, link-local, and (by default) private ranges after
  resolution (the empty `plans/0046-deny-ip-ranges`).
- Upstream DNS servers come from the host (read before lockdown; on macOS
  `/etc/resolv.conf` misses scoped resolvers, gvx's resolver discovery is a
  reference) instead of the proxy container's `/etc/resolv.conf`.

A sentry escape lands in the supervisor, which holds no secrets: the
proxy stays a separate process, as it is a separate container today.

### Guest-side hsh roles

The hsh binary is bind-mounted into the sandbox as `/hsh-workspace` (PID 1:
resolv.conf, session CA, home, network notice, capability drop, rcfile,
exec shell) and `/hsh-sshd` (forwards, `hsh ssh`, OAuth callback delivery).
On macOS the host binary is darwin, so the guest would need a second, Linux
build of hsh. Instead, move these roles to the host side through the SDK:

| Today (in the guest) | With gvx (on the host) |
|---|---|
| resolv.conf, CA bundle, rcfile, network notice | files written into the root filesystem before PID 1 starts, or a read-only mount of a per-session `run/` directory; `Envv`, `WorkDir`, `User`, and `Argv` set the rest |
| `hsh forward`, `hsh run --forward`, managed forwards | `net.dial` per accepted connection |
| listener discovery (`hsh-list@ifup.org`) | `exec.start` of `cat /proc/net/tcp{,6}`, or gvx's auto-publish poller |
| `hsh ssh` | host-side SSH server in `hsh ssh proxy` (still `internal/sshd`) mapping `session`/`exec` to `exec.start` and `direct-tcpip` to `net.dial` |
| `hsh oauth callback` | `net.dial` to the callback port and write the request |
| shell environment snapshot | `exec.start` of `cat /proc/1/environ`, or the env hsh set at boot |
| capability drop, `NO_NEW_PRIVS`, setuid strip | no longer the boundary; gvx ignores setuid by default. Keep a drop only if a guest user is needed for something |

This removes `internal/netsetup` and the in-guest half of `internal/sshd`,
which are the remaining darwin build failures besides `fdbased`. Writing the
session CA into the image's bundles needs an SDK hook: gvx installs host roots
with `Config.HostCACerts` (`hostcerts.Install`); ask for extra roots
(`Config.ExtraCACerts`) or seed files before boot.

### Images

- Labels: `oci.RuntimeConfig` drops `Labels`, so the `org.ifup.hsh` config
  and the OAuth provider label (`oauthProvidersLabel`) are unreadable. Ask
  upstream to expose `Labels` (and the config digest), or read the config
  blob with hsh's own request.
- Image trust (`internal/imagetrust`) is keyed on podman's image ID, which is
  the config digest. Keep that key so trusted images stay trusted.
- Pin the resolved manifest digest in the session at create time so resume
  boots the same layers after `:latest` moves, and keep those layers from
  being pruned while a session references them.
- Local images (`images/build.sh`, `test/fixtures/Containerfile`,
  `podman build -t localhost/...`) are no longer visible. Support
  `hsh image load ARCHIVE` (`docker save`/`podman save`/OCI layout, which
  pkg/oci reads) and a local registry for development.
- Cache location: `$XDG_CACHE_HOME/hsh/oci` (layers, blobs), owned by hsh,
  removed by `hsh wipe`.

### Workspace metadata file

`hostfs` stores POSIX metadata in `.gvx_meta` and `.gvx_meta.lock` at the
mount root, on the host. They show up in `git status` of the user's
workspace. Ask upstream for a metadata path outside the mount (the session
directory); until then add them to `.git/info/exclude` when the workspace is
a git checkout.

The spike found more, even on a Linux host:

- A symlink created in the guest is stored only in `.gvx_meta`. The host sees
  no file at all, so a repository cloned or `npm install`ed in the sandbox
  is missing its symlinks on the host. Host symlinks inside the workspace
  work in the guest. Absolute ones, and ones that escape the workspace, fail
  with `EACCES`.
- A FIFO made in the guest is an empty regular file on the host.

This is a behavior change from podman, where guest symlinks are real host
symlinks. A real symlink is also a risk: an agent can point it at
`~/.ssh` and wait for a host tool to follow it. Ask upstream for an opt-in
that writes real symlinks whose targets resolve inside the mount, and
decide which hsh wants.

### What is lost

- The `container` runtime (`--runtime container`), and with it the nesting
  tests (`test/` nesting cases, plan 0036): running hsh inside a gvx sandbox
  would need gvx inside gVisor. *Verify* whether systrap can run nested;
  otherwise document nesting as unsupported.
- `hsh ls`/`hsh rm` podman pass-through flags (`--filter`, Go `--format`
  templates, `--ctr-ids`, `--ctr-names`, `--ctr-status`, `--ns`).
- `podman logs <pod>-proxy`: proxy logs go to `sessions/<id>/proxy/log`.

## Implementation order

3 → 2 → 1 holds, because each step needs the previous one:

- **3 before 2.** Embedding the SDK while podman still runs the proxy
  container is a working midpoint:
  the supervisor attaches to the same proxy socket that runsc does today
  (it is a host path in the session directory). That tests gvx's
  compatibility with the harness images, TTY, persistence, and suspend before
  anything else changes, and can be shipped behind `--runtime gvx`.
- **2 before 1.** macOS has no podman without a VM, so the proxy must be a
  host process and lifecycle must not depend on pods before macOS works.
- **1 last** is mostly build, signing, testing, and the parts of the design
  already made portable in 3 and 2.

Refinements:

- A **phase 0** comes first: a spike to measure what this plan marks
  *verify*, and the upstream requests, because the network attachment
  blocks phase 3.
- Phase 3 should make choices that pay for 1 early: the portable proxy link,
  guest-side roles moved to the host, and the gvx tcpip copy.
- Phase 2 splits. **2a** (proxy as a host process, session lifecycle from hsh
  state) is what macOS needs. **2b** (deleting the container runtime, runsc
  payload, podman code, and tests) can run in parallel with phase 1.

## Phase 0: spike and upstream (1–2 weeks)

1. Toolchain: gvx needs Go 1.27.4; hsh is on 1.27.3. Bump `go.mod` and CI.
2. Throwaway program: `gvx.New` with `ghcr.io/<owner>/hsh-pi:latest`,
   `RootVolume`, workspace bind, `TTY`, on Linux amd64/arm64 and an Apple
   Silicon Mac. Check: pi, claude-code, codex, vibe, muse-code start and
   run; `dnf install` into the root volume survives a restart; `tty`,
   job control, `SIGWINCH`; Node/Python/git performance against runsc;
   memory overhead; startup time warm and cold; binary size versus the
   current embedded runsc (+30 MB).
3. Network: prototype option A as a patch to gvx against hsh's proxy; also
   check option B's DNS relay behavior so the fallback is understood.
4. Control: `exec.start` with PTY, `net.dial` with loopback fallback, pause
   and checkpoint/restore of a running harness, and whether a checkpoint
   restores after a gvx version change (hsh updates in place).
5. `.gvx_meta` in a git checkout; multiple sessions on one workspace
   (`.gvx_meta.lock`).
6. Open upstream issues/PRs: packet-link network mode; `Labels` and config
   digest in `oci.RuntimeConfig`; extra CA roots or pre-boot file seeding;
   `.gvx_meta` location. Decide whether to vendor a fork while they land
   (gvx is young and mostly one author: pin a version, review its
   security posture before depending on it).

Exit: a written result in this plan and a go/no-go.

### Phase 0 results so far (Linux)

Spike: `plans/prototype/gvx-spike` (`run.sh` builds and runs it; `exec`,
`dial`, and `call` subcommands are control clients; `tty_test.py` drives a
guest terminal; `bench.sh` compares runtimes). gvx v0.24.10002026112300,
Go 1.27.4, Fedora kernel 7.2 on a 2014 Mac mini (Intel i7-4578U, 2 cores
and 4 threads, no SHA-NI), `ghcr.io/philips/hsh-claude-code:latest` (675 MB)
pulled from ghcr by gvx itself.

- **Toolchain:** Go 1.27.4 is fetched through `GOTOOLCHAIN`.
  `z.gfire.dev/gvx` resolves through the module proxy and builds with
  `CGO_ENABLED=0`. The build needs a few GB of temporary space; on a host
  where `/tmp` is a small tmpfs, set `GOTMPDIR`.
- **Backend:** systrap, with no privileges, no podman, and no `/dev/kvm`.
  Lockdown reports subprocesses, unbound file opens, and outbound network
  blocked.
- **Lockdown kills unknown syscalls.** A syscall outside the allowlist kills
  the process with `SIGSYS` (`getrusage`, the CPU profiler). This shaped the
  process model above.
- **Startup:**
  - alpine boots in 36 ms;
  - the harness image takes 17 s the first time (pull and EROFS compile),
    then **2.0 s on every start, even with `pull=never`**: 96% of that is
    `oci.(*LayerCache).openVerifiedLayer` re-hashing every cached layer
    with SHA-256. The memo that skips this lives only in process memory, so
    with one process per session every `hsh run` and `hsh resume` pays it.
    The cost depends on hashing speed: this CPU has no SHA instructions,
    and the Apple Silicon Mac starts the same image in 0.36 s.
    Upstream ask: keep the verification across processes (for example keyed
    on device, inode, size, mtime, and ctime), or let the embedder opt out.
- **Image:** the image works unchanged. Fedora, `HOME=/home/hsh`, the
  image's `PATH`, and `claude --version` (2.1.330) all match what podman
  gives.
- **Root volume:** files written, image files deleted (whiteouts),
  `/home/hsh` state, and a `dnf install -y tree` through NAT all survive a
  restart. The ext4lite file was 111 MB after the install.
- **Terminal (PID 1 with `TTY`):**
  - size, live resize, `SIGWINCH`, Ctrl-Z and `jobs`, Ctrl-C, and the exit
    status all work;
  - `tty` fails with `ttyname error`, and fd 0 shows as `/stdin`. This is
    the same limitation as runsc;
  - `TERM=xterm`.
- **Control socket:**
  - `exec.start` returns the exit status;
  - `/proc/1/environ` and `/proc/1/cwd` give the shell's environment and
    working directory, which is what `/hsh-sshd`'s snapshot does today;
  - `/proc/net/tcp` lists guest listeners;
  - `net.dial` with loopback fallback reached a Python server on guest
    `127.0.0.1:8000`;
  - an exec'd process keeps running after its client is killed;
  - every capability hsh needs is offered on the default policy: `exec`,
    `exec.tty`, `net.dial`, `lifecycle.pause`, `lifecycle.stop`,
    `fs.import`/`fs.export`, `checkpoint.stream`, and `sandbox.stats`.
- **Pause:** `lifecycle.pause` and `lifecycle.unpause` take under 1 ms each,
  and a counter loop in the guest stays frozen while paused.
- **Checkpoint and restore:**
  - `lifecycle.checkpoint` (with `CheckpointDir`) on a running harness with
    a root volume wrote a 540 KB bundle;
  - `gvx.Restore` in a new process resumed it: PID 1 kept running, the
    counter continued, and the root volume was intact;
  - the control client got `EOF` instead of a reply when the checkpoint
    stopped the sandbox;
  - not tested yet: restore across a gvx version change.
- **Memory:** the session process used about 81 MB RSS, plus about 32 MB in
  systrap stub processes, while the guest used 13 MB.
- **Binary size:** a stripped minimal embedder is 41–44 MB (linux/amd64,
  linux/arm64, darwin/arm64). hsh today is 53 MB with runsc embedded and
  21 MB without, so hsh with gvx should land around 60 MB before dropping
  its own `gvisor.dev/gvisor` copy.
- **Workspace:** see [Workspace metadata file](#workspace-metadata-file)
  (`.gvx_meta` in `git status`, guest symlinks invisible on the host).
- **Performance:** `bench.sh`, the same image and commands. Median of three
  warm runs, in ms; the run-to-run range is in parentheses where it
  exceeded 10%. The first, cold runsc run was much slower and is left out.

  | | gvx | runsc (podman) | crun (podman) |
  |---|---|---|---|
  | `claude --version` ×5 | 150 | 129 | 49 |
  | `python3 -c pass` ×20 | 641 | 893 (826–1151) | 280 |
  | `sh -c true` ×200 | 1121 | 1672 (1049–2314) | 196 |
  | copy `/usr/lib64` in the rootfs | 385 | 771 | 213 |
  | write 2000 files in `/workspace` | 221 | 193 | 77 |
  | `git add` + commit of 2000 files | 656 | 627 (595–716) | 185 |
  | `git status` ×10 | 243 | 496 (448–620) | 151 |
  | `find /usr` | 125 | 267 (264–347) | 54 |
  | `rm -rf` 2000 files in `/workspace` | 254 | 190 | 74 |
  | total, including start and teardown | 5885 | 5782 (5134–6154) | 1481 |

  Overall gvx is on par with runsc.
  - gvx is about twice as fast at reading and walking the root filesystem
    (`find`, copies, `git status`).
  - runsc is a little faster at writing workspace files and at running
    small binaries.
  - gvx varies little between runs; runsc varies a lot.
  - gvx's total includes the 2 s of layer hashing on this CPU.
  - Both are 2–6× slower than crun.

### Phase 0 results so far (macOS)

Apple Silicon MacBook Air, Darwin 27.2.0, Go 1.27.4 (fetched through
`GOTOOLCHAIN`):

- `./run.sh` built the spike, ad-hoc signed it with gvx's
  `entitlements.plist`, and booted `alpine:3.20` on `platform=hvf`. Lockdown
  was applied: Seatbelt `(deny default)` with `process-fork` and
  `process-exec*` denied, so subprocesses, unbound file opens, and outbound
  network are blocked.
- `gvx.New` took 1.55 s on the first run, including the pull of alpine.
- All five harness images (`ghcr.io/philips/hsh-{pi,claude-code,codex,vibe,muse-code}:latest`)
  publish `linux/amd64` and `linux/arm64` manifests, so they can run on
  Apple Silicon.
- `hsh-claude-code` (arm64):
  - `uname -m` is `aarch64` and `claude --version` is 2.1.330;
  - `gvx.New` takes 520 ms, but the image may already have been in the
    cache, so this is not a cold pull;
  - a warm start with `pull=never` takes **363 ms**, against 2.0 s on the
    Linux host, because hashing the layers is much faster on Apple
    Silicon.
- **Terminal:** `tty_test.py` gives the same results as on Linux: size,
  resize, `SIGWINCH`, Ctrl-Z, Ctrl-C, and the exit status all work, `tty`
  reports `ttyname error`, and `TERM=xterm`.
- **Root volume and NAT:** `dnf install -y tree` (aarch64) took 20 s;
  `/etc/marker` and `tree` were still there on the next start.
- **NAT lockdown:** with `-net nat` the Seatbelt profile adds
  `(allow network-outbound (remote ip))` and `(allow network-inbound)`, and
  keeps `(deny network-bind)`. hsh's link mode needs only the pre-connected
  proxy socket, so its profile should stay at no network at all.

- **Performance** (`bench.sh`, one run, in ms; the workspace is on APFS),
  with the Linux gvx medians for comparison:

## Phase 3: embed gvx (Linux, podman still present)

1. `internal/sandbox` (new): the `hsh-sandbox` role. Builds `gvx.Config`
   from the session (image digest, `RootVolume` at
   `sessions/<id>/rootfs.ext4`, mounts, env, `Resources`), opens the proxy
   link, control and attach sockets, writes `sandbox.pid`, runs the guest.
2. A runtime interface in `internal/cli` over the operations that call
   podman today (`run.go`, `attach.go`, `detach.go`, `suspend.go`,
   `reaper.go`, `ssh.go`, `forward.go`, `oauth.go`, `ls.go`, `rm.go`,
   `inline.go`, about 60 call sites): create, start, attach, exec, dial,
   pause, stop, status, remove. Implementations: `container` and `gvisor`
   (podman, unchanged) and `gvx`.
3. Images for the gvx runtime through `pkg/oci` with the label/digest
   support from phase 0; image trust keeps its key.
4. Proxy: portable link endpoint and gvx's tcpip; still run in its podman
   container for this phase, listening on the session socket.
5. Attach socket and relay integration; detach/attach, `client.pid`,
   take-over, and the reaper watching `sandbox.pid` instead of
   `podman wait`.
6. Move the guest-side roles to the host (table above): forwards, `hsh ssh`,
   OAuth callback, listener list, CA/rcfile/notice seeding.
7. Suspend on `lifecycle.pause`, and a `Suspended` session state from a
   checkpoint bundle (0052's secondary goal).
8. `--runtime gvx`, recorded in `sessions/<id>/runtime`; `test/gvisor.sh`
   ported as `test/gvx.sh`.

Exit: the functional and security tests pass with `--runtime gvx`; make it
the default.

## Phase 2a: no podman for gvx sessions

1. Proxy as a host process (`hsh-proxy` started per session, `setsid`),
   confined with `hostlockdown` (Landlock + a proxy seccomp filter on Linux,
   Seatbelt on macOS), logging to `sessions/<id>/proxy/log`.
2. Destination IP filtering after resolution (loopback, link-local, private
   by default, the `198.18.0.0/15` placeholders), since the proxy left pasta.
3. Session lifecycle from hsh state: a session is its directory plus live
   `sandbox.pid`/`proxy.pid` (checked with a control `system.ping`, not just
   the pid). Rewrite `hsh ls`, `hsh rm` (`--exited`, `--garbage`, `--all`),
   `hsh detach`, `hsh wipe`'s "sessions running" check, and the reaper on

5. `hsh run` no longer requires podman for gvx sessions.

Exit: a Linux host with no podman, pasta, or subuid ranges runs every hsh
command for gvx sessions.

## Risks and open questions

- gvx maturity and bus factor; its upstream diff gate keeps it close to
  gVisor, but the SDK and hostfs are new code. Pin versions and track
  security fixes; be ready to fork.
- Security model change: runsc separates the gofer from the sentry and runs
  inside podman's user namespace; gvx serves `hostfs` in-process, protected
  by `os.Root` pinning, Landlock/Seatbelt, and seccomp. Review before making
  it the default, and update the security section of `architecture.md`.
- Checkpoint compatibility across hsh/gvx updates; a suspended session that
  cannot restore must fall back to a cold boot from its root volume.
- ext4lite root volumes are a new on-disk format per session; size limits,
  growth, and `fsck` story.
- Binary size and memory per session (one sentry plus systrap stubs per
  session process).
- Whether a single supervisor could host several sessions (gvx supports
  several sandboxes per process; macOS allows one hvf VM per process and
  gvx shares it). Not planned: one process per session keeps sessions
  isolated from each other.
