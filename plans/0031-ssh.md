# SSH into a session: port forwards over the SSH protocol

> **Status: in progress.** Follows plans/0030-forward-ports.md, which designs
> `hsh forward` and the relay verbs this plan builds on. Phase 1 (relay
> `DIAL`/`LIST`) and phase 2 (the SSH server and `hsh ssh-proxy`) are being
> implemented first; shell channels are not started.

## Goal

Make the user's own `ssh` client the interface for reaching a session:

```
laptop$ ssh -L 8000:localhost:8000 hsh-<session>      # the agent's prototype
laptop$ ssh -L 1455:localhost:1455 hsh-<session>      # a browser-redirect OAuth login
```

with `-L` set at connect time or added later (`ssh -O forward`, `~C`), no
second command on the server, and no new multiplexing protocol of our own.
For a purely local setup (hsh on the user's own machine) the same works with
the ProxyCommand pointing at `hsh` directly.

## Why SSH, and why not a listening sshd

The SSH protocol gives channel multiplexing, flow control, half-close, and a
client every user already has. 0030's exec-per-connection costs a `podman
exec` per TCP connection; here a session is one `podman exec` carrying
many channels.

A listening sshd would need a long-lived process per session (today only the
reaper survives a detach), host keys, authorized keys, and a TCP port that any
local user on a shared server can reach. None of that is needed. The
transport is already authenticated by the user's login to the machine that
runs podman, so the SSH server speaks over **stdio**, with no listener.

## Design

```
laptop ssh ──ProxyCommand──► ssh server hsh ssh-proxy hsh-<id>
                               └─ podman exec -i <pod>-ws /hsh-workspace-inner --ssh-stdio
                                    (pod netns; SSH server on stdin/stdout)
                                     └─ direct-tcpip "localhost:8000"
                                          └─ TCP 10.77.0.2:7788  "DIAL 8000"
                                               └─ relay in inner netns ──► 127.0.0.1:8000
```

Client configuration, printed by `hsh ssh-config [--host server]`:

```
Host hsh-*
    ProxyCommand ssh server hsh ssh-proxy %h
    StrictHostKeyChecking no
    UserKnownHostsFile /dev/null
    LogLevel ERROR
```

Host-key checking is off because the SSH layer adds no identity: the server
generates an ephemeral key per connection, and the trust is in the outer
transport. For a local setup the ProxyCommand is `hsh ssh-proxy %h`.

### 1. Relay verbs (shared with 0030)

`DIAL <port>` (ack `OK` or `ERR <reason>`, then a raw stream) and `LIST`
(listening TCP ports in the inner netns), plus the source-address check
(`10.77.0.1` only) and correct half-close, as specified in 0030. The SSH
server dials through the relay; it never needs to enter the inner netns.

### 2. The SSH server (`internal/sshd`, `golang.org/x/crypto/ssh`)

Runs inside the workspace container via the mounted hsh binary
(`/hsh-workspace-inner --ssh-stdio`), serving one connection on stdin/stdout,
in the pod netns where the relay is reachable. Authentication is `none`.

Accepted:

- `direct-tcpip` channels whose destination host is `localhost`, `127.0.0.1`,
  or `::1` and whose port is 1 to 65535. The destination is dialed with
  `DIAL <port>` through the relay. The originator address the client sends is
  ignored.
- global request `hsh-list` (an extension) returns the sandbox's listening
  ports, backing `hsh forward --list` and the client-side port hints.

Rejected, always:

- `direct-tcpip` to any other host. Allowing it would turn the relay into an
  outbound path that bypasses the egress policy.
- `tcpip-forward` / `cancel-tcpip-forward` (`ssh -R`): that is the sandbox
  reaching toward the user's side, not the reverse.
- `streamlocal-forward@openssh.com`, `direct-streamlocal@openssh.com`,
  agent forwarding, X11, and `env` requests.
- `session` channels, until phase 3.

`-D` (SOCKS) is a client-side feature that turns into `direct-tcpip` with
arbitrary destinations, so it works only toward the sandbox's loopback and the
docs do not advertise it.

### 3. The host command (`internal/cli/ssh.go`)

`hsh ssh-proxy [--session ID] [NAME]`: resolve the session (`NAME` as
`hsh-<id>` or `<id>`; with neither, the workspace directory's only session, as
`hsh oauth callback` does), check the workspace container is running, then run
`podman exec -i <pod>-ws /hsh-workspace-inner --ssh-stdio` with stdin, stdout,
and stderr passed through. There is no host-side protocol logic and no daemon.
`hsh ssh-config` prints the stanza above.

### 4. Shell channels (phase 3, optional)

A `session` channel with `shell`/`exec`/`pty-req` would give a second
terminal in the running session (and scp, VS Code Remote-SSH). The hard part
is that the server runs in the pod netns with the container's capabilities,
so it must put the shell where the existing one is: enter the inner netns,
drop all capabilities but CAP_DAC_OVERRIDE, set NO_NEW_PRIVS, use the same
environment (proxy variables, CA bundle, home, workspace) and the same
resolv.conf. This is a security-sensitive feature that needs its own review,
so it stays out of phases 1 and 2.

## OAuth

`ssh -L 1455:localhost:1455 hsh-<session>` delivers the browser redirect
straight into the waiting login. The token exchange still goes out through the
egress proxy, where plan 0011's capture swaps real tokens for phantoms. This
completes the automatic flow that plan 0022 left as future work; `hsh oauth
callback` stays as the fallback. Some CLIs choose a random port; the user
reads it from the printed URL, or from `hsh forward --list`.

## Security

- No listener on the host: the only way in is a process the user starts
  themselves, over a transport that already authenticated them.
- The SSH server process is in the workspace container but is not reachable
  from the sandbox's shell: its stdio belongs to `podman exec`, and it holds
  more capabilities than the shell, so the kernel refuses ptrace from the
  shell. It holds no secrets.
- The destination restriction and the `-R` rejection are the load-bearing
  checks, tested explicitly (below). Without them SSH would become an egress
  bypass.
- A forwarded port exposes the agent's code to the user's browser; a page at
  `localhost:8000` can probe other localhost ports in that browser. That is the
  same as running the dev server locally.
- On a shared server, local users cannot reach the session (there is no
  listener), but the `ssh -L` listener on the user's own machine is on the
  user's own loopback.

## Phases

1. **Relay verbs.** `DIAL`/`LIST`, source check, half-close (the foundation
   shared with 0030).
2. **SSH server and `hsh ssh-proxy`.** `direct-tcpip` to the sandbox's
   loopback, rejection of everything else, `hsh ssh-config`, docs. Unit tests
   with an in-process `ssh.Client`; functional test with a real `ssh -L`.
3. **Shell channels,** reviewed separately.
4. **`hsh forward`** (0030) can be reimplemented over the same server so that
   the exec-per-connection path goes away, or kept as the no-ssh-config path.

## Verification

Unit tests (in-process client against the server, over `net.Pipe`):

- `direct-tcpip` to a loopback listener round-trips, with large transfers and
  half-close in both directions
- destinations `example.com`, `10.77.0.1`, `192.168.1.1`, and `0.0.0.0` are
  rejected without any dial; `tcpip-forward`, streamlocal, agent, X11, and
  `session` channels are rejected
- a dial to a closed port fails the channel with a clear reason, and a later
  open on the same connection still works

Functional (`test/functional.sh`, new step), with the real `ssh` client and the
ProxyCommand stanza against a running session:

1. `ssh -L` to a server inside the sandbox: `curl` through the forward
   returns the body; multiple concurrent connections over one SSH connection
2. `ssh -L 9999:example.com:443` is refused and logs no proxy activity
3. a fake loopback-OAuth harness in the sandbox (`test/oauthsrv`) receives the
   redirect through `-L` and the exchange is phantom-rewritten
4. the same works on a detached session; the SSH connection ends when the
   session stops
5. no ports are opened on the host by `hsh run` or by `hsh ssh-proxy`

## Open questions

- A ProxyCommand that runs `ssh server hsh ...` needs `hsh` on the server's
  non-interactive PATH. `hsh ssh-config --hsh-path` can embed an absolute
  path.
- Whether the client should be able to ask which session to use when several
  match the workspace directory is a naming question; `hsh-<id>` host names
  make the session explicit, so for now a bare `hsh-*` always carries an id.
