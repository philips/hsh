# DNS egress through the proxy

## Goal

DNS resolution currently does not work inside the workspace: its
`/etc/resolv.conf` points at `127.0.0.1` (the workspace's own network
namespace, where nothing listens), so every local lookup fails instantly
(`getent hosts api.mistral.ai` → no result). Proxied tools (curl, apk, pi)
do not notice because the HTTP proxy resolves upstream hostnames itself.
Tools that resolve locally — or users debugging with `getent`/`nslookup` —
get nothing.

The goal: DNS works inside the sandbox, gated by the same `network.allow`
policy as every other egress, so "allowing DNS" does not open an
unrestricted name-resolution channel.

## Why policy matters here

The workspace has no direct route anywhere, so resolved names cannot be
reached directly — the TCP layer still enforces the allowlist. But an
unrestricted resolver would still be a real hole: DNS tunneling lets the
workspace exfiltrate data (e.g. the mounted project) to any
attacker-controlled domain, encoded in query names, without ever opening
a TCP connection the proxy could check. So DNS must be allowlist-gated
like HTTP.

## Options

### A. DNS forwarder inside the proxy (recommended)

Run a small DNS server (UDP + TCP 53) on `10.77.0.1` — the address the
workspace can already reach — inside the proxy container, and point the
workspace's `resolv.conf` at it.

- Allowlist enforcement: the query name is matched against
  `network.allow` with the same rules as HTTP (exact, `*.wildcard`,
  case-insensitive, trailing dot ignored). Denied → `REFUSED`.
- Allowed queries are forwarded to the upstream resolvers from the proxy
  container's `/etc/resolv.conf` (the pod's resolvers, e.g. pasta's
  `169.254.1.1`, tailscale `100.100.100.100`, the LAN resolver).
- Denials are recorded in a **separate `dns_denied` table** in the same
  SQLite database (decision, see below). They never enter the HTTP review
  list, so noisy lookups cannot be auto-allowed by mistake.
  `harnessh proxy-denied --dns` lists them. When `proxy-auto-allow` allows
  a host, matching `dns_denied` rows are marked allowed as well. The running
  proxy hot-reloads the allowlist, so DNS follows within a second, no
  restart.
- The workspace's `resolv.conf` becomes `nameserver 10.77.0.1` (plus
  short timeout options). No new routes, no `ip_forward`, no iptables.
- No new config knob is needed: an empty `network.allow` already means
  "resolve nothing", which is the existing default posture.

### B. Direct DNS ("allow port 53")

Give the workspace `/32` routes to each upstream resolver via the veth,
enable `ip_forward` in the pod network namespace, and restrict traffic to
those resolver IPs to port 53 with iptables (without the restriction the
resolver host — which can be the LAN router — would be exposed on every
port).

Rejected for the default: more moving parts (route setup, `ip_forward`,
iptables rules, resolver discovery, v6 resolvers), no DNS-level policy
(any name resolves — the DNS tunneling channel stays open), and it
exposes resolver hosts to the sandbox.

### C. Open forwarder (no DNS policy)

Same as A but resolving every name. Simplest, but leaves the DNS
tunneling exfiltration channel open. Rejected as the default; could be a
future escape hatch.

## Recommended design (A) details

- New file `internal/proxy/dns.go` in the existing proxy package (it
  shares the hot-reloaded allowlist state and the denial DB directly — no
  callback plumbing). Uses `github.com/miekg/dns` (pure Go, keeps the
  `CGO_ENABLED=0` static build).
- Two listeners (`udp` and `tcp`) on `10.77.0.1:53`, started right after
  the HTTP listener binds (the workspace parent already waits for the
  proxy before releasing the shell, so DNS is up before any tool runs).
- Handler: take `msg.Question[0].Name`, strip the trailing dot, check
  `p.allowed(name)`:
  - allowed → forward the raw message to the upstream resolvers
    (`dns.Client.Exchange`, trying each nameserver from
    `/etc/resolv.conf` in order, UDP with TCP fallback on truncation),
    write the response back. No caching in v1.
  - denied → log, record in the denial DB (`host` = query name,
    `target` = `name:53`), reply `REFUSED`.
- PTR/SRV/other query types for non-allowlisted names are refused the
  same way; the policy is purely name-based.
- The proxy's own upstream resolution is unaffected (it uses the pod's
  resolvers directly, so there is no loop).
- Workspace entrypoint change: `writeResolvConf` points at
  `netsetup.HostIP` instead of `127.0.0.1`.

- `internal/proxy/proxy.go`: start/stop the DNS listeners with the HTTP

- `internal/workspace/workspace.go`: `resolv.conf` → `nameserver 10.77.0.1`.

## Verification

1. In the sandbox (host allowlisted): `getent hosts api.mistral.ai`
   resolves to a real address.
2. `getent hosts google.com` (not allowlisted) fails; the proxy log shows
   the refusal; `harnessh proxy-denied` lists `google.com`.
3. `harnessh proxy-auto-allow` → `getent hosts google.com` now resolves
   (real DNS through the proxy, no restart).
4. `harnessh proxy-denied` → review list cleared.
5. Regression: proxied curl/apk/pi unchanged; direct connections still
   blocked — `curl --noproxy '*' https://api.mistral.ai` now gets past DNS
   and fails at connect (no route), proving resolution and egress control
   are independent.
6. Hot reload: adding a host to `network.allow` in the config file makes
   its DNS resolve within ~1s without restarting the sandbox.
7. `test/functional.sh` extended with the above (using `getent hosts`,
   which needs no extra packages) and still passes end to end.

## Decisions

- **Separate table (decided):** DNS denials are recorded in a `dns_denied`
  table, not the shared `denied` pending list. `harnessh proxy-denied`
  (default) shows only HTTP egress denials; `harnessh proxy-denied --dns`
  shows pending DNS denials; `proxy-auto-allow` never auto-allows DNS
  denials but marks matching `dns_denied` rows allowed when it allows a
  host. This keeps telemetry/PTR noise out of the TOFU review flow.

## Open questions

- Upstream transport: UDP with TCP fallback (recommended) vs UDP only.
- Caching: skip for v1; a small TTL-respecting cache would cut upstream
  load if the workspace resolves heavily.
