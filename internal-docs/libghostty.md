# libghostty-vt in hsh

`internal/vt` runs a real terminal emulator in the relay so hsh can
repaint sessions, draw over them, and know when the byte stream is
between escape sequences (see `internal-docs/architecture.md`, plans
0025 and 0026). The emulator is Ghostty's `libghostty-vt`, consumed as
an official release — never a tip build or a third-party blob.

## Layout

    internal/vt/libghostty/          Go wrapper around the libghostty-vt C API
    internal/vt/libghostty/wasmvt/   the wasm module turned into generated Go
        ghostty-vt-small.wasm        the official small wasm build, committed
        vt.generated.go              generated from the wasm by wasm2go
        PROVENANCE                   release version, sha256, SHA256SUMS line

`internal/vt/ghostty.go` is the `vt.Emulator` implementation on top of
the wrapper. The wrapper is vendored from the MIT-licensed
`code.selman.me/hauntty/libghostty` module and is otherwise kept
upstream-shaped; hsh's own no-comment rule does not apply to it.
Every file in the vendored package carries the same
`//go:build goexperiment.simd` tag as `vt/ghostty.go`, so a build
without the experiment falls back to the `none` backend instead of
failing. The generated code trips `go vet`'s unreachable-code check,
so CI vets `$(go list ./... | grep -v internal/vt/libghostty/wasmvt)`.

## Provenance

The wasm comes from the official release directory
`https://release.files.ghostty.org/libghostty-vt/VERSION/` (the small
build: smallest binary, fine for hsh's use). `tools/bump-libghostty.sh`
verifies the download against the release's own `SHA256SUMS` before
using it. `PROVENANCE` records the version, the sha256 of the committed
blob, and the `SHA256SUMS` line it was verified against;
`internal/vt/provenance_test.go` fails if the committed blob's hash
drifts from that pin.

The only other third party in the chain is the wasm2go build that
turns the wasm into Go (below). It is a build-time code generator: its
output is committed, so a compromised generator is visible in the diff
of `vt.generated.go`.

## The wasm2go pipeline

The binding is generated by `github.com/seruman/wasm2go` (the SIMD-capable
fork of `github.com/ncruces/wasm2go`, pinned in `tools/bump-libghostty.sh`),
patched with `internal-docs/libghostty-wasm2go.patch`:

    go tool flags: -unsafe -nanbox -pkg wasmvt
    input:        internal/vt/libghostty/wasmvt/ghostty-vt-small.wasm
    output:       internal/vt/libghostty/wasmvt/vt.generated.go

The generated code (and therefore every build of hsh) needs
`GOEXPERIMENT=simd` and amd64/arm64 (see DEVELOP.md).

Upstream `ncruces/wasm2go` has no SIMD translation at all: its
maintainer is waiting for Go's SIMD experiment to ship before taking
the per-target work (ncruces/wasm2go#50 — the portable `simd` API
translates slower than scalar, so only `simd/archsimd` per target is
worth it, and that breaks his single-generated-file design). The
`seruman/wasm2go` fork — written by the hauntty author — implements
the `simd/archsimd` route on its `simd` branch, but only "selected
SIMD instructions": the opcode mix of the Ghostty wasm he translated
at the time. New libghostty-vt releases built with a different Zig
can emit opcodes the fork never saw.

When a new release adds one, generation dies with
`unsupported opcode (SIMD): 0xFD 0xNN`; grow the patch with a case in
`code_simd.go` and a helper in `helpers/simd.go` (the generator embeds
that file's source into its output). The two current additions
(`i16x8.add_sat_u`, `i16x8.max_u`) come from the escape-sequence
parameter parser, which does saturating arithmetic on `u16` params
(`param_acc +|= c - '0'` in Ghostty's Parser.zig) and `@max` clamps
in stream.zig; both map straight onto `simd/archsimd.Uint16x8`
methods. They are ordinary fixed-width-SIMD opcodes, not exotic ones
— the gap is purely that the fork's coverage is demand-driven.

## Bumping to a new release

    ./tools/bump-libghostty.sh X.Y.Z

downloads, verifies, regenerates, rewrites `PROVENANCE`, and runs the
vt and relay tests. Then review the diff:

- `vt.generated.go` regenerating is expected; skim it for size only.
- If the libghostty-vt C API changed, the wrapper ports go in
  `internal/vt/libghostty` and the wrapper tests
  (`internal/vt/libghostty/wasm_test.go`, ported from upstream to plain
  `testing`) should catch the behavior. The 1.0.0 port touched:
  option and data-kind enum renumbering (`terminal.go`,
  `key_encoder.go`, `snapshot.go`), the formatter moving from a
  one-shot options struct to per-option `ghostty_formatter_set` calls
  (`formatter.go`), `GhosttyGridRef`/`GhosttySelection` losing their
  size prefix (`grid_ref.go`, `formatter.go`), and key event UTF-8
  moving to the `GhosttyString` struct (`key_event.go`).

Wasm ABI notes that are easy to get wrong (from the release's
`wasm.h`): functions that return a struct take an extra *first*
argument pointing at the result — `ghostty_key_event_get_utf8(out,
event)`; `size_t` is 4 bytes; by-value struct parameters are passed as
pointers.

## Why not a wasm runtime

plans/0025 measured the alternatives. wazero would make bumps trivial
but adds a runtime dependency and interpreter overhead; wasm2go keeps
hsh a static pure-Go binary with the emulator inlined, at the cost of
the generator patch described above.
